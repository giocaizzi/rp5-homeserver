# CI/CD

## Workflows overview

Workflows in `.github/workflows/`: **`ci.yml`** (PR + push → `main`): `make check` (`docker compose config` + `shellcheck` + `hadolint`), gitleaks, `terraform fmt`/`validate`/`plan` for `cloud/**` (PRs only), plan comment (updated in place), single `check` required check. **`pr-title.yml`** (PR): scoped Conventional-Commit title lint. **`leak-check.yml`** (PR, incl. `edited`): fails when the diff, commit messages, title or body contain a value from the `LEAK_PATTERNS` secret (domain, emails, Pi user, cloud identifiers; one per line, also set as a Dependabot secret); reports where, never what; required check `Leak check`. **`release-please.yml`** (push `main`): versioning/changelogs/tags only (App-token; no deploys). **`apply-cloud.yml`** (push `cloud/**`): `terraform apply` via `cloud-production` env (GCS state + GCP WIF) — Terraform stays plan-reviewed-on-merge. **`deploy-infra.yml`** (on **`infra` release**): self-hosted Pi runner, `sync_infra.sh --local`, env `pi-production`. **`deploy-services.yml`** (on **service release**): per-released-stack Portainer webhook on the Pi runner, env `pi-services`. **`deploy-workers.yml`** (on **`mcp-connector` release**): GitHub-hosted runner, `npm ci` + `typecheck` + `wrangler deploy --env` matrix over the servers in `workers/mcp-connector/registry.json`, env `cloudflare-workers`. **`swarm-health.yml`** (cron */10): Pi runner, ntfy `swarm` alert for services below desired replicas ≥10 min (secret `NTFY_SWARM_TOKEN`). Deploy envs expose the Deployments-tab audit + optional "Required reviewers" gate. Full flow: [Releases](./releases.md).

## Details

Seven GitHub Actions workflows. Versioning/tagging (`release-please.yml`, `pr-title.yml`) and the PR gate (`ci.yml`) run off PRs/`main`; the **runtime deploys are release-gated** (`deploy-infra.yml`, `deploy-services.yml`, `deploy-workers.yml`), while `cloud/` Terraform stays apply-on-merge (`apply-cloud.yml`). Full release/versioning flow: **[docs/releases.md](./releases.md)**; deploy setup: [docs/gitops.md](./gitops.md).

**`cloud/` (apply-on-merge).** `ci.yml` runs on every PR → `main` and short-circuits via `paths-filter` when `cloud/**` didn't change. When it did: `terraform fmt -check → init (GCS backend) → validate → plan`, then posts a plan comment (updated in place) on the PR. The single required status check is the `check` job (always runs, asserts no upstream job failed; `lint` and `secrets` must succeed) — robust to skipped jobs and renames. `apply-cloud.yml` (formerly `cd.yml`) runs on push to `main` touching `cloud/**` and does `terraform apply -auto-approve` from the `cloud-production` environment. Terraform stays **plan-reviewed-on-merge, not release-gated** (release-gating IaC would let `main` diverge from applied infra). Flip "Required reviewers" on that environment to add a human gate.

**`infra/` (release-gated).** `deploy-infra.yml` fires when release-please publishes the **`infra` release** (the bare `v*` tag), on a **self-hosted runner on the Pi** (label `rp5`, installed via `scripts/setup_pi_runner.sh`). It runs `sync_infra.sh --local` (no SSH — already on the Pi). `--local` mode excludes `secrets/` from the `rsync --delete` (secrets are gitignored, live only on the Pi) and never writes them, so a **new** `infra/` secret file makes the release deploy fail (`Stack deployment failed`) until a non-local `PI_SSH_USER=<user> DOMAIN=<domain> ./scripts/sync_infra.sh` has written it from Secrets Manager — run that once before cutting the release that adds the secret. Env `pi-production`; needs its environment secrets `PI_DEPLOY_USER` and `CLOUDFLARE_ZONE_NAME` (passed as `DOMAIN`, which `infra/docker-compose.yml` requires; manual runs export it too). Triggers only on `release`/`workflow_dispatch`, never `pull_request`, so fork code never runs on the Pi.

**`services/` (release-gated).** `deploy-services.yml` fires when release-please publishes a **service release** (`<stack>-v*`): a `detect` job parses the stack name from the tag, then a matrix `deploy` job runs on the **Pi self-hosted runner** and POSTs that stack's Portainer GitOps webhook **locally** (resolves the Portainer host to loopback → nginx → Portainer, never leaving the Pi). This sidesteps Cloudflare's WAF, which 403s GitHub's cloud egress IPs even with a valid CF Access service token. Non-service releases (`infra`, `cloud`, `mcp-connector`) no-op.

**`workers/mcp-connector/` (release-gated).** `deploy-workers.yml` fires on the **`mcp-connector` release** (`mcp-connector-v*`; other releases skip) and runs `npm ci`, `npm run typecheck`, then `wrangler deploy --env <id>` as a matrix over the servers in `workers/mcp-connector/registry.json` (a `servers` job builds the matrix; `workflow_dispatch` takes one id or `all`). Code-only: per-env Worker secrets and KV were created once by `workers/mcp-connector/deploy.sh` and persist. `render-config.sh` generates each `env.<id>` from the registry and fills the private values from **secrets** on `cloudflare-workers` (`DOMAIN`, `ALLOWED_EMAILS`, optional `MCP_GROUPS`, `KV_ID_<ID>`) before `wrangler deploy -c wrangler.deploy.jsonc`; `make lint` validates the registry. Private values go in secrets, never variables: GitHub prints a step's `env:` values in its log header, and only secrets are masked there. Env `cloudflare-workers` needs secrets `CLOUDFLARE_API_TOKEN` (Account → Workers Scripts:Edit, scoped to the account; use a dedicated token, not the Terraform one) and `CLOUDFLARE_ACCOUNT_ID`, plus the placeholder secrets. Adding a server: one `registry.json` entry, then bootstrap its KV and secrets with `deploy.sh` ([runbook](../workers/mcp-connector/README.md#-adding-a-server)). Terraform is deliberately not used for Workers (it would need a prebuilt bundle and own bindings/secrets). Env `pi-services`; needs secrets `PORTAINER_URL` and `WEBHOOK_ID_<STACK>` per stack. Each service stack must be set to **Webhook** (not Polling) GitOps auto-update in Portainer. Adding a stack: add the secret **and** a `WEBHOOK_ID_<STACK>` line to the deploy job env.

**Auth (cloud/).** GCP via Workload Identity Federation — no SA key in GitHub; Actions exchanges its OIDC token for a short-lived credential, restricted to this repo by the WIF provider's attribute-condition. Cloudflare via API token stored as an **environment secret** (`CLOUDFLARE_API_TOKEN`) on `cloud-plan` and `cloud-production`. Tunnel secret stored as `TUNNEL_SECRET`, same environments. State backend: GCS, bucket name in environment secret `TF_STATE_BUCKET`, prefix hardcoded in `cloud/backend.tf`.

**Variable wiring.** Both workflows declare a `TF_VAR_*` env block under the plan/apply step that maps GH variables/secrets to terraform inputs. Only non-identifying values are **repo-level variables** (`GCP_REGION`, `BACKUP_RETENTION_DAYS`, `TF_VERSION`); credentials and every identifier (zone, account/zone IDs, GCP project, buckets, WIF provider, service account) are **environment secrets**, set on both `cloud-plan` and `cloud-production` (never repository-wide) — the zone name (`CLOUDFLARE_ZONE_NAME`) and the `<SVC>_USERS` email lists are secrets because GitHub prints a step's `env:` values in the public log header and only secrets are masked there; Terraform marks `zone_name` and the `*_users` inputs `sensitive` (and every output), and `ci.yml` scrubs every `LEAK_PATTERNS` value and user email from the plan before commenting it (IDs in refresh lines and provider-returned values are never `sensitive`; the log is masked, the comment is not) so plan output and the PR plan comment never show them. The `cloud-plan` / `cloud-production` environments hold those secrets and give the Deployments-tab audit trail and the optional approval gate. Adding a new terraform variable means: add `variable "..."` to `cloud/variables.tf`, add `TF_VAR_<name>: ${{ vars.<NAME> }}` (or `secrets.<NAME>` for anything private, plus `sensitive = true` on the variable) to **both** `ci.yml` and `apply-cloud.yml` plan/apply steps, set the GH var or secret (`gh variable set` / `gh secret set -e cloud-plan` and `-e cloud-production`), and append it to the bootstrap script's printed checklist so future bootstraps stay accurate. List-typed terraform vars must be JSON-encoded strings (e.g. `'["a@x.com","b@y.com"]'`); **user-list secrets use `${{ secrets.<NAME> || '[]' }}`** so an unset value defaults to an empty list (Access locked, no users) instead of crashing `terraform plan` with "Missing expression".

**Adding a public service (the recipe).** (1) nginx: `server_name <svc>.*` (wildcard: the domain is never committed) + `globals.conf` backend map entry `<svc>.*` + `defaults.conf` HTTP→HTTPS redirect; anything else that needs the domain reads `${DOMAIN}` (compose) or `{{HOMEPAGE_VAR_DOMAIN}}` (homepage). (2) terraform: CNAME, tunnel ingress entry (host-correct `http_host_header` and `origin_server_name`), `<svc>_users` variable, Access policy + self-hosted Access app, `<svc>_url` output. (3) GH: set the `<SVC>_USERS` secret (JSON array) on environments `cloud-plan` and `cloud-production` and add `TF_VAR_<svc>_users: ${{ secrets.<SVC>_USERS || '[]' }}` to both `ci.yml` and `apply-cloud.yml`. (4) Land the nginx change as `feat(infra):`/`fix(infra):` and **cut the infra release** — that fires `deploy-infra.yml` (`sync_infra.sh`), which tests and reloads nginx for the changed config. Do not hand-edit VERSION. Bootstrap script (`scripts/bootstrap_cloud_cicd.sh`) prints the canonical variable/secret/environment checklist when re-run.
